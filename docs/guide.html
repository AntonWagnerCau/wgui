Widget reference

Guide

The whole library is three ideas: you redeclare the UI every frame, elements are identified by their labels, and only the differences are sent to the browser. Everything below follows from those.

The frame loop

A Context owns the servers and the frame buffers. Create one at startup and keep it alive for as long as you want the UI. 

let mut ctx = w_gui::Context::new();

loop {
    {
        let mut win = ctx.window("Controls");
        win.slider("Speed", &mut speed, 0.0..=10.0);
    } // `win` dropped here, releasing the borrow on `ctx`

    ctx.end_frame();
}

ctx.window(name) returns a Window that mutably borrows the context, so only one window can be open at a time. Scope it with a block or drop(win) before opening the next one. Calling ctx.window("Controls") again later in the same frame simply appends more elements to that window.

end_frame closes the frame: it diffs the declarations you just made against the previous frame and hands the resulting messages to the WebSocket thread. An element you stop declaring disappears from the UI. That is what makes conditional UI work without any teardown code.

Required

end_frame must be called once per frame. Without it nothing is ever sent, and the previous frame is never swapped in, so every element looks new forever.

There is no fixed tick rate inside the library. It updates as fast as you call end_frame. For a UI attached to a non-realtime program, a small sleep is usually right: 

ctx.end_frame();
std::thread::sleep(std::time::Duration::from_millis(33)); // ~30 Hz

Windows

Every element belongs to a window, named by the string you pass to ctx.window(). Windows are laid out by the frontend into a responsive masonry of cards; their order follows the order in which you first declare them each frame. 

{
    let mut win = ctx.window("Simulation");
    win.slider("Gravity", &mut gravity, -20.0..=20.0);
}
{
    let mut win = ctx.window("Rendering");
    win.checkbox("Shadows", &mut shadows);
    win.slider("Exposure", &mut exposure, 0.0..=8.0);
}

Windows are cheap. Grouping by subsystem is usually clearer than one long panel, and the window name is part of every element id inside it, so two windows can both have a slider labelled "Scale" without colliding.

Tabs

Windows can be grouped into tabs — whole pages you switch between in the browser. A tab is named like a window, and hands out windows that belong to it: 

{
    let mut tab = ctx.tab("Simulation");
    let mut win = tab.window("Fire");
    win.slider("Heat", &mut heat, 0.0..=10.0);
}
{
    let mut tab = ctx.tab("Diagnostics");
    let mut win = tab.window("Timings");
    win.kv("Frame", "16.7 ms");
}

The tab bar appears at the top center once any tab is declared, and the active tab is remembered per browser. Windows created directly with ctx.window() are not bound to a tab and show on every page. The tab name is part of the element ids inside it, so two tabs can each have a window named "Settings" without colliding, and each tab keeps its own drag-arranged card layout.

Element identity

You never allocate widget handles. An element's id is derived from its container and its label: 

"Rendering::Exposure"        // window "Rendering", label "Exposure"
"Rendering::Exposure#1"     // second widget with the same label
"Rendering::__grid::Speed"  // inside a grid inside that window

Duplicate labels within the same container are disambiguated by an occurrence counter, so repeating a label is legal, but the counter is positional: it depends on how many widgets with that label came before it this frame. Two rules follow.

  • Renaming a label replaces the element. The old id is no longer declared, so it is removed, and a new one is added. This is harmless for values you own, but it resets nothing on the Rust side and does move the element to the end of its window until the next reorder message corrects it.
  • Keep duplicate-label sets stable. If you emit "Item" once under one condition and three times under another, the #1 and #2 ids come and go. Prefer labels that carry the distinguishing information (&format!("Item {i}")).
Tip

Labels are also what the user reads. Making them unique and descriptive satisfies both the identity model and the person looking at the panel.

Reading interaction

Input widgets write through the &mut reference you pass and return a Response: 

let r = win.slider("Speed", &mut speed, 0.0..=10.0);

if r.changed() {
    // the value is different from what it was before this frame
    rebuild_something(speed);
}

if win.button("Reset").clicked() {
    speed = 5.0;
}
Method Meaning
clicked() An edit arrived from the browser this frame, whether or not it altered the value. For buttons this is the press itself, true for exactly one frame.
changed() An edit arrived and the value actually differs from the old one. This is the one to gate expensive work on.

Edits are queued on a channel and drained on demand, keyed by element id, so only the latest value per element survives a burst. A fast slider drag produces one edit per frame, not one per pixel of movement. An edit for an element you did not declare this frame stays queued and is applied whenever that element is declared again.

Display-only widgets (label, stat, progress_bar, mini_chart, plot, kv, image, section, separator) return nothing. They are pure output.

Grids

win.grid(cols, |grid| { … }) lays its children out in a fixed number of columns. Grids nest. 

win.grid(3, |grid| {
    grid.stat("Generation", &generation.to_string(), None, AccentColor::Coral);
    grid.stat("Fitness", &format!("{fitness:.2}"), Some("max 0.95"), AccentColor::Green);
    grid.stat("Iterations", &iterations.to_string(), None, AccentColor::Blue);
});

win.grid(2, |grid| {
    grid.progress_bar("Solution A", 0.26, AccentColor::Green);
    grid.progress_bar("Solution B", 0.25, AccentColor::Purple);

    grid.grid(2, |inner| {
        inner.checkbox("Loop", &mut looping);
        inner.checkbox("Trace", &mut trace);
    });
});

A grid supports most of the widget set, including nested grids, but not horizontal, section or set_accent. See the availability matrix.

Horizontal rows

win.horizontal(|h| { … }) packs its children into a single row that the frontend never splits across columns. It is meant for toolbars and compact input pairs. 

win.horizontal(|h| {
    h.label("Preset");
    h.text_input_inline("name…", &mut preset_name);
    if h.button_accent("Save", AccentColor::Green).clicked() {
        save_preset(&preset_name);
    }
    if h.button_accent("Delete", AccentColor::Red).clicked() {
        delete_preset(&preset_name);
    }
});

Buttons and text inputs created on a Horizontal use inline variants that drop the label column, which is why text_input_inline takes a placeholder rather than a label. A horizontal row cannot contain a grid or another row.

Sections and accents

win.section("Title") emits a header, win.separator() a divider, and win.set_accent(color) sets the accent color for the window it is called on, which tints the window's header dot and its default widget highlights. 

let mut win = ctx.window("Renderer");
win.set_accent(AccentColor::Purple);

win.section("Exposure");
win.slider("EV", &mut ev, -8.0..=8.0);

win.separator();

win.section("Denoiser");
win.checkbox("Enabled", &mut denoise);

Widgets that take an explicit AccentColor argument (stats, progress bars, charts, status indicators, accent buttons) override the window accent for themselves.

Configuration

Three constructors:

use w_gui::{Context, ContextOptions, Glow};

// Defaults: localhost, port 9080, title "wgui", no favicon, subtle glow.
let ctx = Context::new();

// Same, but start the port search somewhere else.
let ctx = Context::with_port(7000);

// Everything explicit.
let ctx = Context::with_options(ContextOptions {
    start_port: 9080,
    title: "Pyromancer Debug".to_string(),
    favicon: Some(std::fs::read("icon.png").unwrap()),
    public: false,
    glow: Glow::Strong,
});
Field Default Effect
start_port 9080 First port tried. HTTP takes the port, the WebSocket takes the next one, and the search advances in steps of two until a free pair is found (up to 1000 ports).
title "wgui" Browser tab title. HTML-escaped before it is substituted into the page.
favicon None PNG bytes served at /favicon.png. When None, that path returns 404.
public false false binds 127.0.0.1; true binds 0.0.0.0 so other machines on the network can connect.
glow Glow::Subtle Strength of the accent glow on slider fills and thumbs, progress bars, status dots, stat values and chart lines. Glow::Off removes it entirely, Glow::Strong roughly doubles the blur radius. Focus rings and card shadows are unaffected.

The chosen ports are readable at runtime with ctx.http_port() and ctx.ws_port(), which is how you print a correct URL when the default port was taken.

Security

public: true exposes an unauthenticated page that can write into your program's state to everyone who can reach the port. Use it on trusted networks only.

Headless mode

If no free port pair is found, construction does not fail and does not panic. The context logs a warning and runs degraded: windows and widgets still work, values still round-trip through your own variables, and end_frame becomes a no-op. http_port() and ws_port() both return 0.

This is deliberate: a debug UI should never take down the program it is attached to, and code paths that read Response::changed() keep compiling and running unchanged in CI or on a machine with the ports occupied.

Threads and lifetime

A live context owns two named threads, wgui-http and wgui-ws, plus one short-lived thread per WebSocket handshake. Your frame loop only ever touches channels, so it is never blocked by a slow or half-dead browser tab: reads, writes and handshakes all have timeouts, and clients that break them are dropped.

Context is Send + Sync, so it can be stored in an ECS resource, a Mutex, or a struct that moves between threads.

Backpressure

The channel to the WebSocket thread holds two batches. If your frame loop outruns the network, end_frame logs at debug level and skips that frame's update rather than blocking. Since each frame's diff is computed against the previous declared frame and the server keeps its own mirror, a skipped batch is not lost state: the next frame in which a value changes re-sends it.

Shutdown

Dropping the context signals both threads and joins them, so the ports are fully released before the drop returns (roughly a 200 ms HTTP poll interval in the worst case). That wait is what makes an in-process restart land on the same ports again, which matters because an already-open browser tab keeps pointing at the old URL. 

drop(ctx);                    // ports released here
let ctx = Context::new();     // binds the same pair again

Wire protocol

Not something you need for normal use, but useful when debugging with the browser's network inspector. Both directions are JSON, tagged by a type field.

Server to browser

Message Sent when
snapshot A client connects. Carries every element currently in the server's mirror.
add An element id appears that was not declared last frame.
update An element's value, label or metadata changed. Label and metadata are omitted when unchanged.
remove An element declared last frame was not declared this frame.
reorder The declared order of a window's elements differs from what the client would have after applying the batch (adds append, removes delete).

All messages produced by one end_frame are sent as a single JSON array in one WebSocket frame.

Browser to server

Message Sent when
set The user edited a widget. Carries the element id and the new typed value.
reorder_window The user dragged a window card. Window order is not persisted across restarts.

The HTTP server serves exactly four paths: / and /index.html (the embedded frontend), /favicon.png, and /ping. The frontend polls /ping while disconnected and only opens a WebSocket once it answers, which keeps failed attempts out of the browser's reconnect backoff.

Patterns

Conditional UI

Just do not declare it. Nothing else is needed.

win.checkbox("Advanced", &mut show_advanced);

if show_advanced {
    win.slider("Bounces", &mut bounces, 1..=32);
    win.slider("Roulette Depth", &mut roulette, 1..=16);
}

Rolling history for charts

mini_chart and plot take a slice, so keep a fixed-length buffer and push into it once per frame.

const HISTORY: usize = 120;

frame_times.push(dt_ms);
if frame_times.len() > HISTORY {
    frame_times.remove(0);
}

win.mini_chart("Frame Time", &frame_times, Some(" ms"), AccentColor::Teal);

Multi-series plots

Each series carries its own color and an autoscale flag. With autoscale = true a series is normalized independently, which is what you want for values in different units; with false it shares the plot's scale, which is what you want when magnitudes are comparable. 

win.plot_with_autoscale(
    "Timings",
    &[
        ("GPU ms", &gpu_ms, AccentColor::Green, false),
        ("CPU ms", &cpu_ms, AccentColor::Blue, false),
        ("VRAM MB", &vram, AccentColor::Orange, true),
    ],
    Some("Frame"),
    Some("Value"),
);

Images

image and image_button take a base64 data URI, so any encoder that produces PNG or JPEG bytes works. Build the URI yourself and hand it over: 

let uri = format!("data:image/png;base64,{}", base64_encode(&png_bytes));
win.image_with_size("Preview", &uri, 256, 256);

The full URI is re-sent whenever it changes, so update thumbnails at a rate you would be comfortable pushing over a socket rather than every frame.

Attaching to an existing engine

Store the context wherever your per-frame state lives and call end_frame at one fixed point in the frame, after everything that wants to contribute widgets has run. 

struct Engine {
    gui: w_gui::Context,
    // …
}

impl Engine {
    fn frame(&mut self) {
        self.simulate();
        self.render();
        self.debug_ui();       // every subsystem declares its windows
        self.gui.end_frame();  // exactly one call per frame
    }
}

Pitfalls

  • Forgetting end_frame. The UI stays empty and the previous frame never advances. One call per frame, no more, no less.
  • Holding a Window across end_frame. It will not compile, since the window borrows the context. Scope it.
  • Building labels from changing values. &format!("Speed {speed:.2}") changes the id every time the value moves, so the element is destroyed and recreated each frame. Put the value in the widget, not the label, or use kv for read-only pairs.
  • Expecting clicked() to persist. It is true for the single frame in which the edit is consumed.
  • Assuming the port. If 9080 is taken the context moves to the next free pair. Print ctx.http_port() instead of hardcoding the URL.
  • Re-encoding large images every frame. The data URI travels over the WebSocket in full on every change.
