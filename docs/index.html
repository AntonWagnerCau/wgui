What it is

w-gui runs an HTTP server and a WebSocket server on two threads inside your process. Your program describes the UI every frame with plain method calls; the library diffs that description against the previous frame and pushes only the changes to any connected browser tab. Edits made in the browser travel back and land in your variables on the next frame.

There is no windowing library, no GPU context, no event loop to integrate with, and no native dependency. The entire dependency set is tiny_http, tungstenite, serde, serde_json, log, and indexmap. The frontend is a single HTML file compiled into the binary.

Immediate mode

No retained widget tree to keep in sync. Declare what you want this frame; it appears.

In-process

Two background threads, no separate binary, no IPC to set up.

Remote-friendly

It is a web page. Tune a headless render job from a laptop on the same network.

Diff-based

Only changed elements go over the wire, batched into one WebSocket frame per tick.

Never fatal

If no port is free, the context degrades to headless and your widget calls still work.

Send + Sync

Context is both, so it can live in a resource container or behind a lock.

Install

The crate is published as w-gui and imported as w_gui.

cargo add w-gui

Or by hand:

[dependencies]
w-gui = "0.22"

Quickstart

Create one Context at startup, then rebuild the UI every frame. Widgets take &mut references to your own state: they read it to draw and write to it when the browser sends an edit. 

use w_gui::{AccentColor, Context};

fn main() {
    let mut ctx = Context::new();

    let mut color = [1.0f32, 0.4, 0.1];
    let mut speed = 5.0f32;
    let mut enabled = true;
    let mut frame_times: Vec<f32> = Vec::new();

    loop {
        {
            let mut win = ctx.window("Simulation");
            win.set_accent(AccentColor::Coral);

            win.checkbox("Enabled", &mut enabled);
            win.slider("Speed", &mut speed, 0.0..=10.0);
            win.color_picker("Fire Color", &mut color);

            win.separator();
            win.section("Stats");
            win.mini_chart("Frame Time", &frame_times, Some(" ms"), AccentColor::Teal);

            if win.button("Reset").clicked() {
                speed = 5.0;
            }
        }

        ctx.end_frame();

        // ... your engine / simulation frame ...
    }
}

The context prints its URL on startup. Open it in a browser: 

wgui: UI available at http://127.0.0.1:9080
Tip

The Window borrows the context, so scope it (or drop it) before calling end_frame. Multiple windows are just multiple ctx.window("…") calls.

How it works

Every widget call pushes an element declaration (id, kind, label, value, metadata, owning window) into a per-frame buffer. Element ids are derived from the window name and the widget label, so the same widget keeps its identity across frames without you managing handles.

end_frame compares this frame's declarations against the previous frame's and emits the minimal set of add / update / remove / reorder messages, which are sent to the WebSocket thread as a single batch. That thread keeps a mirror of the current UI state so a tab opened at any moment receives a full snapshot and is immediately in sync.

In the other direction, the browser sends a set message when the user drags a slider or types in a field. It is queued on a channel and consumed by the matching widget call on your next frame, which writes the new value through the &mut reference and reports it via Response.

The guide covers the frame lifecycle, ids and duplicate labels, containers, ports and options, and the threading model in detail.

Examples

Two runnable examples ship with the crate:

git clone https://github.com/AntonWagnerCau/wgui
cd wgui
cargo run --example demo
cargo run --example dashboard
  • demo — a tour of the individual widgets and their interactions.
  • dashboard — grids of stat cards, progress bars, sparklines and plots driven by a fake simulation, i.e. what a real monitoring panel looks like.

When to use it

w-gui is built for debug and tuning panels attached to long-running programs: renderers, simulations, trainers, servers. It is a good fit when you want to change a parameter without recompiling, watch a value evolve, or drive a headless process from another machine.

It is not a general application UI toolkit. There is no layout engine beyond grids and rows, no text editing beyond single-line fields, no theming API, and rendering latency is bounded by your frame rate and the WebSocket round trip. For an in-window immediate-mode UI drawn by your own renderer, reach for egui instead.
